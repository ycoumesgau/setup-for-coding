# Internationalisation

A product launched in one language still makes its language choices on day one: every
hard-coded sentence, every locale-free URL and every silent fallback becomes a rewrite when
the second language arrives. Past a handful of languages, translation becomes a pipeline that
writes to the database, and it fails like any other pipeline.

## When it matters

- At kickoff, even for a single-language product.
- When a second locale is added to content or to the interface.
- When translation by a model is about to write published content.

## Decide

1. **Where the texts live.** Keys in code, values in a store that can be localised later: a
   CMS, or an ICU catalogue (plurals, variables) while there is no CMS. One locale resolver
   for the whole product.
2. **What the schema speaks.** English names and enum values; a value shown to users goes
   through a label table, never printed raw.
3. **URLs.** One URL per language (`/en`, `/fr`): search engines send no `Accept-Language`,
   so a page that varies by header is indexed in one language. Do not translate slugs.
4. **The switch.** A cookie set by the language switch, then `Accept-Language`, then the
   default, as a temporary redirect with `Vary`.
5. **Fallbacks.** Visible or absent, never silent on a public URL.
6. **Who translates, and who reads it.** A human, a model at publication, or both; a "to
   review" state and a per-locale lock that the pipeline obeys.

## Options

| Option | Gives | Costs | Choose it when |
| --- | --- | --- | --- |
| ICU catalogue files in the repository | Plurals, tooling, typed keys | A deploy per wording change | No CMS yet, or a consumer app |
| Keys in code, values in a CMS | Wording edited without deploy | One more store to seed and sync | The product already has a CMS |
| Per-domain dictionaries with their own resolvers | Nothing to set up | No common format, no plurals, divergent fallbacks | Never |
| Locale grain (`fr-CA`) | Regional variants | One row and one write per locale | A market needs it |
| Language grain (`fr`) | Fewer rows and writes | No regional variants | The default |

## Default

No hard-coded text, keys in code, values in a localisable store; stable error codes from the
API, translated in the interface; `Intl` formatters given the locale, never a literal one;
`lang` and `dir` set on `<html>` by the server; CSS logical properties; rich content stored as
a JSON tree whose text leaves can be extracted; a locale segment in every route.

When a second locale arrives: publication status is per locale, and publishing a locale
requires its own required fields; public reads disable the locale fallback; a page missing in
one language redirects to the other rather than showing borrowed text under the wrong URL;
`hreflang` lists only published languages, plus `x-default`.

This stops being enough past about ten locales: then content and SEO pivots, and a policy per
locale (full translation, adaptation, alias), become worth their weight.

## Traps

- **Fallback text under the wrong URL.** With the CMS fallback on, a French page with an
  empty field showed the English text. On a CMS with per-locale status, publishing French
  failed until French had its own title.
- **Routes ahead of texts.** A consumer project routed 210 locales while its interface texts
  covered at best 22 languages in 7 domains, and its sign-in app had French hard-coded. A
  Hebrew page got `dir="rtl"` with an English or French interface. Nothing checked for
  hard-coded text.
- **Counts that look cheap.** 46 full translations, 96 adaptations and 68 aliases: by
  calculation, about 141 model calls and 209 sequential writes per publication. Aliases were copied into the
  database instead of resolved on read. One edited field once triggered all 210 locales, until
  translation ran on publication only.
- **200 is not written.** 208 HTTP 200 responses, about 42 locales actually stored: two
  concurrent updates of one document lost the locale rows. Remedy: sequential writes, then a
  read-back with the fallback off.
- **Less fail-closed than claimed.** Validation checked only shape, so a translation left in
  the source language passed; the rich-text reinjection kept source text for a missing
  string; a failed adaptation wrote a copy of its pivot marked valid; locked locales were never
  filtered from targets, so the next job overwrote human corrections; the "needs review" flag
  was read nowhere. A cheap model broke the rich-text JSON every time: extract the text
  leaves, translate strings, reinject them.
- **The pipeline skipped the project's own outbox rule.** The job was sent from a save hook;
  a send error was logged and swallowed; no event id, no per-document concurrency key. Cost
  was logged, never stored or capped. Trigger translation through a persisted outbox row.
- **Right-to-left audited by hand.** A script flagged physical CSS properties and missing RTL
  stories but ran in no CI; fonts loaded only the Latin subset, so Arabic, Hindi or Chinese
  pages would fall back to system fonts.

## Hold it with a check

- A lint rule against string literals in interface code; the capture run fails on a raw key.
- A test that public reads find no text when a locale is empty (seen red with the fallback on).
- A CI check for physical CSS properties once a right-to-left locale exists.
- Pipeline tests: a locked locale is never written; a translation identical to its source,
  or a missing rich-text string, blocks the locale; a write is followed by a read-back.
- Human reading has no check, and the source project never wired its "needs review" flag.
  We recommend: a locale nobody on the team reads, and any legal, pricing or contractual
  text, waits in "to review" until a person approves it, and the pipeline reads that state.
